# SAML NameID mappings

MemberID stores one immutable mapping for each registered `(SP, Member)` pair. The SP belongs to one organization; the Member must belong to that organization. An existing mapping is reused across password, phone, DingTalk and Feishu authentication, profile changes, restarts and signing-key rollover. Matching contact attributes never merges Members. This mapping does not change the Member ID or the OIDC `(iss, sub)` identity.

## Formats and lifetime

The registration's `nameIdFormat` is either `persistent` (the default) or `unspecified`. These select the standard URIs `urn:oasis:names:tc:SAML:2.0:nameid-format:persistent` and `urn:oasis:names:tc:SAML:1.1:nameid-format:unspecified`. Configure it through `saml sp apply` or the private registration API. The console displays the current format and preserves it on edits; console creation defaults to persistent.

Persistent identifiers are random pairwise pseudonyms generated by MemberID. Unspecified identifiers use an explicitly provisioned legacy value, or the same random allocation when no mapping exists and the request permits creation. Neither mode derives a value from a phone number, email, display name, or external provider subject. Email remains a separate [opt-in attribute](member-email.md); `emailAddress` is not a supported NameID format.

An omitted NameIDPolicy or its empty/unspecified Format does not constrain the configured output format. Other requested formats must match the registration. If a NameIDPolicy is present, omitted `AllowCreate` means false. An existing legacy or generated mapping can be used with `AllowCreate=false`; an absent mapping cannot. Incompatible requests receive a signed `InvalidNameIDPolicy` response without an assertion.

The format can change with the current SP revision only while the SP has no mappings. Once any mapping exists, the format is fixed for that SP. Every mapping value is permanent: no update, removal, reassignment or replacement operation exists. Values are unique within an SP and can independently exist in another SP's namespace. Disabling or retiring the SP retains its mappings and entity ID reservation. Blocking a Member or revoking a factor stops eligible issuance without releasing its identifiers. Do not delete rows to reuse an identity.

The response uses MemberID's metadata URL as NameQualifier and the registered SP entity ID as SPNameQualifier. Arbitrary old values are supported only with `unspecified`. Importing another IdP's persistent identifier and original qualifiers is outside this implementation. The [SAML Core specification, sections 3.4.1.1 and 8.3](https://docs.oasis-open.org/security/saml/v2.0/saml-core-2.0-os.pdf) defines format negotiation and persistent identifier requirements. A consumer that keys accounts by the old issuer, qualifiers, or format needs its own explicit account migration when changing IdPs; copying a value alone does not guarantee compatibility.

## Provision an existing application account

Only the installation operator CLI can inspect or provision mappings. Possession of the private management API credential, a console administrator role, or an authenticated Member session does not authorize these operations. There is no HTTP mapping endpoint, self-service binding, bulk importer, or migration UI. The operator must independently verify the intended Member and the application's old account identifier before provisioning: the identifier may grant access to that existing application's data.

Use a protected installation and `MEMBERID_DATABASE_URL` as in [operator setup](operations.md). Prefer registering the SP disabled with `nameIdFormat: "unspecified"`, provisioning its intended legacy accounts, then enabling it with the inspected current registration revision. Provision before the first login: an existing generated mapping cannot be overwritten, even with the same value or while the SP is disabled.

```sh
memberid saml sp inspect --directory ./installation --id legacy-sp
memberid saml nameid provision --directory ./installation \
  --organization org_REPLACE_WITH_ORGANIZATION \
  --sp legacy-sp --member mbr_REPLACE_WITH_MEMBER \
  --value old-account-42 --revision 1
memberid saml nameid inspect --directory ./installation \
  --organization org_REPLACE_WITH_ORGANIZATION \
  --sp legacy-sp --member mbr_REPLACE_WITH_MEMBER
```

`--revision` is the expected current **SP registration revision**, not a mapping revision. Inspection never allocates a missing mapping. Retired registrations reject provisioning. A stale revision, different existing value, already generated mapping, or value reserved by another Member fails without changing either mapping. Inspect the registration and mapping after an uncertain response. Repeating an identical legacy provisioning at the current SP revision returns the original record without another audit event.

Values are exact, case-sensitive UTF-8 text of 1–256 Unicode code points. Leading/trailing whitespace, control characters and XML-invalid characters are rejected; values are never trimmed or normalized. Supply only identifiers verified in the consuming application's namespace. CLI arguments and output may be visible in local shell history or process inspection; protect operator access and avoid sharing raw output containing account identifiers.

The JSON result records `organizationId`, `serviceProviderId`, `memberId`, `value`, `nameIdFormat`, `source`, `createdBy` and `createdAt`. Source is `legacy` with creator `installation-operator`, or `generated` with creator `protocol`. Provisioning and its `saml.nameId.provision` management event commit atomically. The event records the actor, Member scope and mapping; a failed audit write rolls back the mapping. Protocol authentication events and service logs do not include the NameID value. Registration edits retain their existing transactional audit.

SP row locking serializes initial allocation, legacy provisioning and format changes. Unique database constraints reserve both `(SP, Member)` and `(SP, value)`. A concurrent first login either uses the committed legacy mapping or wins random allocation, after which provisioning returns a conflict. It cannot issue one value and replace it with another.

## Validation and deployment boundary

Focused PostgreSQL tests cover authorization, organization isolation, conflicts, immutable reservations, retirement, audit rollback, and concurrent provisioning versus allocation. Real HTTP tests reuse a legacy mapping with `AllowCreate=false`, verify the signed format policy error, and exercise the same generated and legacy identities through all four synthetic authentication methods and OIDC SSO. The [independent packaged consumer](saml-interop.md) seeds an existing application account, confirms that a provisioned NameID opens that account, and repeats after a MemberID process restart without creating another account.

Schema 27 retains the mapping provenance introduced in schema 26. Startup never migrates or deletes data; use the [explicit forward upgrade and recovery workflow](database-upgrades.md) for schema 26 installations. Acceptance does not establish arbitrary old-IdP migration, GitLab SAML compatibility, browser inspection, or real external-provider verification.
